Monolithic Deep-Dive: Every Reason It Fails on Hardware

This section goes deeper into why a monolithic kernel — one CU handling CRC + TCP + SHA via a runtime mode switch — is the wrong direction for hardware, even though it seems simpler from a software perspective.

🔴 Problem 1: Dead Logic That Still Costs Real Silicon

In a monolithic kernel, Vitis HLS synthesizes all three algorithm datapaths into every single CU regardless of which one runs at runtime. The if (mode == CRC) control logic becomes a hardware multiplexer — it does not eliminate the unused circuitry.

Think of it like building three full kitchens inside one house and only ever cooking in one at a time. The other two still consume floor space, plumbing, wiring, and construction cost — whether or not anyone uses them.

// What the old monolithic kernel looks like on silicon
void kernel(data_in, data_out, mode, tables) {
    if (mode == CRC)  → process_crc(...)       // CRC datapath always synthesized
    if (mode == TCP)  → process_tcp_checksum()  // TCP datapath always synthesized
    if (mode == SHA)  → process_hash()          // SHA datapath always synthesized
    // A hardware MUX at the output selects which result to forward
    // but ALL THREE sets of logic gates physically exist in every CU
}

🔴 Problem 2: BRAM Explosion Per CU

The CRC kernel requires a 16×256 uint32_t parallel slice table in BRAM:

// kernel.cpp line 671 — inside every CRC path
uint32_t crcTables[16][256];  // = 16 × 256 × 4 bytes = 16,384 bytes per CU
#pragma HLS BIND_STORAGE variable=crcTables type=ram_1p impl=bram
#pragma HLS ARRAY_PARTITION variable=crcTables complete dim=1
// "complete dim=1" = 16 independent BRAM blocks instantiated per CU
// so it can read all 16 table rows simultaneously → II=1

In a monolithic CU these 16 BRAMs are present in every instance — even when the CU is processing a TCP or SHA packet. In a split design, TCP and SHA CUs have zero BRAM overhead (they use DDR).

Design style BRAM blocks per CU For 8 CU instances
Split SHA CU 0 (uses DDR) 0 BRAM blocks consumed
Split CRC CU ~16 ~128 BRAM blocks
Monolithic CU (all 3) ~16 (CRC tables always present) ~128 BRAM blocks — even when doing SHA work

🔴 Problem 3: Mixed Memory Interfaces Create Port Conflicts

CRC is optimized for HBM (low-latency, many banks). TCP/SHA are optimized for DDR (wide 512-bit streaming). A monolithic CU needs both memory systems simultaneously:

Monolithic CU: conflicting memory requirements ┌─────────────────────────────────────────────────┐ │ Monolithic CU │ │ gmem0 → CRC needs HBM (low-latency random access) │ gmem0 → TCP/SHA need DDR (wide 512-bit stream) │ tables → HBM bank (CRC-only feature) │ │ → port conflicts, wider AXI, harder routing │ └─────────────────────────────────────────────────┘ Split CUs: each has exactly the right interface ┌────────────────┐ ┌──────────────────┐ ┌──────────────────┐ │ CRC CU │ │ TCP CU │ │ SHA CU │ │ gmem0 → HBM │ │ gmem0 → DDR[0/1] │ │ gmem0 → DDR[0/1] │ │ gmem1 → HBM │ │ (512-bit wide) │ │ (512-bit wide) │ └────────────────┘ └──────────────────┘ └──────────────────┘

🔴 Problem 4: Critical Path Is the Worst of All Three

When HLS compiles a monolithic function, it must find one clock period that satisfies timing across all combinational paths inside it — including paths from all three algorithms. The critical path is set by the slowest one after they are combined inside the same RTL module:

Kernel (standalone) HLS Fmax estimate Dominant critical path
calculate_crc 275.55 MHz 16-wide BRAM lookup + XOR reduction tree
calculate_tcp_checksum 411.00 MHz 4-level partial-sum adder chain
calculate_sha256 291.64 MHz SHA-256 round: Σ₀/Σ₁, Ch, Maj + additions

In a monolithic kernel all three logic clouds share the same routing region. The resulting combined critical path after place-and-route is always worse than any individual HLS estimate because: (1) Vivado has to fit more logic into the same area, increasing wire lengths and (2) the logic from one algorithm interferes with the placement of another.

🔴 Problem 5: Scaling Is All-or-Nothing

Every time you add one monolithic CU, you add one full copy of all three algorithms. You cannot say "I need 2× more SHA throughput" without also doubling CRC and TCP logic. With split CUs you can add 4 SHA CUs independently and leave CRC and TCP unchanged.

❌
Bottom line on monolithic: The split design failed timing at 24 CUs with −0.118 ns. A monolithic design offering equivalent throughput would need ~8 CUs but each would be ~3× larger in area and routing complexity. The timing problem would be at least as bad — likely worse — and the design permanently wastes silicon on two out of three idle algorithms at any given moment.

What "Timing" Means & Why Reducing Frequency Helps

This is one of the most important concepts in FPGA design, and it directly explains your −0.118 ns failure and how reducing the clock frequency can fix it without changing any logic.

What Is a Clock Period?

Every flip-flop (register) in the FPGA captures its input on a clock edge. The clock period is how much time exists between two edges — this is the maximum time any combinational logic path has to propagate its result from one register to the next.

At 220 MHz:  clock period = 1 / 220,000,000 = 4.545 ns
At 200 MHz:  clock period = 1 / 200,000,000 = 5.000 ns
At 300 MHz:  clock period = 1 / 300,000,000 = 3.333 ns
Clock edge Clock edge │ │ ▼ ▼ ──────┬─────────────────────┬────── clock │◄─── 4.545 ns ──────►│ ← budget at 220 MHz │ │ [FF] ──→ [LUT] → [LUT] → [LUT] → [LUT] ──→ [FF] ↑ all this logic must complete within 4.545 ns the longest such path is called the CRITICAL PATH

What Is Slack?

Slack is the difference between the available time budget and the actual propagation time of the critical path:

Slack = Clock Period − Critical Path Delay

Your build result:
Slack = 4.545 ns − 4.663 ns = −0.118 ns    ← NEGATIVE = timing FAILURE

If you had 200 MHz instead:
Slack = 5.000 ns − 4.663 ns = +0.337 ns    ← POSITIVE = timing PASSES ✅

A negative slack means the logic path is physically too slow for the requested clock speed. The signal from one register cannot reach the next register in time before the next clock edge arrives. The FPGA would sample incorrect (transitioning) data — it would be broken hardware.

Why Does Routing Congestion Make Slack Worse?

With 24 CUs crammed onto the U280, the FPGA fabric is very dense. Vivado cannot always place two logically connected elements close together — it has to route signals across longer distances on the chip, and longer wires have more resistance and capacitance, which means longer propagation delays.

Sparse placement (few CUs) → short wires → fast paths: [FF_A] ──short wire──→ [FF_B] delay = 2 ns slack = +2.5 ns ✅ Dense placement (24 CUs, congested) → long detour wires → slow paths: [FF_A] ──long detour─────────────→ [FF_B] delay = 4.7 ns slack = −0.1 ns ❌

Why Reducing Frequency Helps — Without Changing Any Code

Your critical path delay is a physical property of the placed and routed circuit — it does not change when you change the target frequency. What changes is how much time you are giving that path:

Frequency Clock period (budget) Critical path delay Slack Result
220 MHz 4.545 ns ~4.663 ns −0.118 ns ❌ FAIL
210 MHz 4.762 ns ~4.663 ns +0.099 ns ✅ PASS
200 MHz 5.000 ns ~4.663 ns +0.337 ns ✅ PASS (comfortable)
ℹ️
The critical path delay (~4.663 ns) is an estimate — actual routing may shift it. But the key insight is: you only need to recover 0.118 ns of slack. Dropping from 220 → 210 MHz adds 0.217 ns of budget — more than enough. You keep all 24 CUs, you just run them slightly slower. At 200 MHz you have a comfortable margin.

The Throughput Cost of Lowering Frequency

Reducing from 220 → 200 MHz is a 9% frequency drop. Since throughput scales linearly with clock speed (CRC = N bytes/cycle × clock), you lose about 9% of throughput per CU. For context:

CRC at 220 MHz: 16 bytes/cycle × 220M cycles/s ≈ 3.52 GB/s per CU
CRC at 200 MHz: 16 bytes/cycle × 200M cycles/s ≈ 3.20 GB/s per CU  (−9%)

With 16 CRC CUs:
220 MHz → ~56 GB/s aggregate CRC throughput
200 MHz → ~51 GB/s aggregate CRC throughput

A small price to pay for hardware that actually works.
✅
Practical recommendation: Try --kernel_frequency 210 first. This recovers 0.217 ns of slack (nearly 2× what you need) while only costing ~4.5% throughput. If that still fails, drop to 200 MHz.

HLS Pipeline Internals: What II=1 Actually Means

The build log reports results like "Pipelining result: Target II = 1, Final II = 1". Understanding this is key to knowing how fast the kernels actually run.

Initiation Interval (II)

II = 1 means the pipelined loop can accept a new input every single clock cycle — the best possible result. Think of a car assembly line: even though it takes 10 stations to complete a car, a new car can enter station 1 every cycle because all stations work in parallel.

II = 2 means 2 cycles must pass before the next input can start — effectively halving throughput. Your TCP kernel has this problem on its scalar fallback path due to a memory port bottleneck:

WARNING: [v++ 200-885] II Violation in 'word_loop':
Unable to schedule bus request on port 'gmem0' due to limited memory ports.
Final II = 2.  (needs two loads from same port in one cycle → must stagger)
Loop Kernel Final II Throughput impact
block_loop CRC 1 16 bytes processed per cycle ✅
vec_word_loop TCP 1 64 bytes per cycle (vectorized path) ✅
word_loop TCP scalar 2 1 byte-pair per 2 cycles ⚠️
round_loop SHA 1 1 SHA-256 round per cycle ✅
expand_words SHA 2 Data dependency in schedule ⚠️

The DATAFLOW Pragma in CRC

The CRC kernel uses #pragma HLS DATAFLOW which allows three sub-functions to overlap like a pipeline of pipelines:

#pragma HLS DATAFLOW
read_input(data_in, inByte0...inByte15, ...);   ← loads 16 bytes, fans into 16 streams
                      ↓ FIFO streams (depth=64)
process_blocks(crcTables, inByte0...inByte15, ...outStream);  ← 16-parallel table lookup
                      ↓ outStream FIFO
write_output(outStream, numChunks, crc_out);    ← drains results to DDR/HBM

// While process_blocks computes chunk N,
// read_input is already loading chunk N+1 into the byte streams.
// All three functions run simultaneously — latency is hidden.

Emulation Tiers: sw_emu vs hw_emu vs hw

Vitis provides three build targets with very different fidelity levels. This is exactly why the design can pass sw_emu and fail hw.

Target What runs Checks timing? Build time Use for
sw_emu Pure C++ on CPU, kernels as libraries ❌ Never Seconds Algorithm correctness during development
hw_emu RTL (Verilog) simulation with AXI bus models ❌ No real timing Minutes Interface bugs, DMA, AXI protocol
hw Full Vivado synthesis + place & route → bitstream ✅ Yes — must meet clock Hours Real deployment on physical FPGA

sw_emu always passes for correct algorithms because: there is no clock (time doesn't exist), memory accesses are instant C++ pointer dereferences, there is no routing, and all HLS pragmas like #pragma HLS PIPELINE are silently ignored. A logically correct but physically infeasible design always passes sw_emu.

hw_emu passes but hw can fail because hw_emu runs the Verilog RTL in a simulator with modeled AXI buses — it catches interface bugs but does not perform physical P&R and cannot detect timing violations.

Looking at your actual build log timeline for the 24-CU hw build:

[12:30:43] Synthesis complete (~12 min — HLS RTL → Vivado netlist)
[13:10:07] Logic optimization complete (17 min)

[16:39:01] Routing complete (1h 46min — many rip-up/reroute iterations)
[16:59:37] FAILED — timing not met, slack: -0.118 ns

Practical Workload Sizing Guide

Choosing the right CU mix is the most impactful design decision. Here's a framework for thinking about it rationally.

Step 1: Know Per-CU Throughput

CU type Throughput per CU @ 220 MHz Bottleneck
calculate_crc ~3.5 GB/s (16 bytes × 220M/s) BRAM read bandwidth
calculate_tcp_checksum ~14 GB/s vectorized (64 bytes × 220M/s) DDR memory bandwidth
calculate_sha256 ~0.4–1 GB/s (compute-bound: 64 rounds / 64-byte block) Compute (SHA rounds)

SHA is the slowest per CU because it is compute-bound: 64 rounds of complex arithmetic are needed for every 64-byte block. TCP benefits enormously from the 512-bit wide bus.

Step 2: Watch the DDR Bandwidth Ceiling

TCP and SHA both alternate between DDR[0] and DDR[1]. Each U280 DDR4 channel has ~19.2 GB/s peak bandwidth. If you add too many TCP/SHA CUs they will compete for the same two channels and memory becomes the new bottleneck:

# DDR[0]: serves TCP_0, TCP_2, SHA_0, SHA_2, SHA_4 ... (all even indices)
# DDR[1]: serves TCP_1, TCP_3, SHA_1, SHA_3, SHA_5 ... (all odd indices)

# Example: 1 TCP CU + 5 SHA CUs sharing DDR[0]:
TCP:  14 GB/s  +  SHA: 5 × 1 GB/s = 19 GB/s  ← right at the DDR ceiling
# Adding a 6th SHA CU on DDR[0] would not improve throughput — DDR is saturated

Step 3: Recommended Configurations

Use case CRC TCP SHA Total Notes
Fix timing now (220 MHz) 8 2 2 12 Half the CUs → much more routing slack
Keep all 24 CUs (200 MHz) 16 4 4 24 Drop freq only, no CU changes, −9% throughput
CRC-heavy network traffic 14 1 1 16 Good timing with max CRC throughput
Security/hash-heavy 4 2 10 16 Watch DDR ceiling; 10 SHA ≈ 10 GB/s
TCP validation only 2 6 2 10 ~84 GB/s TCP aggregate; DDR limited
🎯
Quickest path to working hardware: Change --kernel_frequency 220 to --kernel_frequency 210 in the linker command, rebuild the xclbin (Stage 2 only, ~5 hours), run on hardware. This recovers 0.217 ns of slack with only ~4.5% throughput cost and requires zero changes to kernel code or CU counts.
