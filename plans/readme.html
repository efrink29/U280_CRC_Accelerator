U280 CRC Accelerator: Hash Extension + Runtime Readme

Last updated: 2026-02-10

This document explains what was implemented for hash support and also how runtime execution works between host, manager, and kernel.

What Was Implemented

  • Added a new mode so one kernel can run CRC, TCP checksum, or SHA-256.
  • Implemented SHA-256 in the FPGA kernel path (chunk-by-chunk).
  • Implemented software SHA-256 on host side as a golden reference.
  • Updated manager output handling for SHA-256 (8 words per chunk, not 1).
  • Added input safety checks for chunk alignment and invalid chunk sizes.
  • Added file input support in host app with -i/--input_file.
  • Added plans/run_swemu_compare.sh for interactive testing of CRC/TCP/SHA.

Runtime Flow (Host -> Manager -> Kernel)

  1. Host parses args + config: src/host.cpp reads CLI, checks xclbin path, and loads KernelConfig.
  2. Host creates manager: FpgaManager(xclbin,...) initializes OpenCL objects and worker threads.
  3. Manager loads xclbin: creates cl::Program, discovers CUs named calculate_crc:{CRC_i}.
  4. Manager sets up buffers: input/output buffers plus table buffers (real CRC tables for CRC mode, zero table otherwise).
  5. Host submits work: mgr.calculate_crc(data, cfg, ...) creates tasks.
  6. Worker launches kernel: manager sets kernel args, writes input, launches kernel, reads output.
  7. Kernel dispatches by mode: TCP path, HASH path, or default CRC path.
  8. Host compares results: software reference vs FPGA output and prints OK/MISMATCH.

Key Terms You Asked About

  • What is cfg? A variable of type KernelConfig that carries run settings (polynomial/init/xor/chunk size/mode/hash algo).
  • What is cfg.checkMode? Mode selector sent to kernel: 0 = CRC, 1 = TCP checksum, 2 = HASH.
  • What is argument 7? Kernel arg index in setArg(7,...) (0-based). It maps to kernel function parameter mode.
  • What is a "path"? In code, a path means the execution route/branch taken by conditions (CRC path, TCP path, HASH path).

Kernel dispatch behavior: mode 1 -> TCP path, mode 2 -> HASH path, otherwise CRC path.

When Loading a New xclbin: Responsibilities

  • Host app responsibility: provide xclbin path and valid runtime config/input shape.
  • Manager responsibility: load/program xclbin, find CUs, bind args correctly, transfer data, launch/readback.
  • Kernel responsibility: keep function signature + arg order compatible, implement mode behavior, and write expected output layout.

Checklist when kernel changes:

  • If signature changes, update all manager setArg(...) mappings.
  • Keep mode enum values aligned between manager and kernel (0/1/2).
  • If output shape changes, update manager output sizing (wordsPerChunk).
  • If CRC table contract changes, update table generation/upload logic.
  • Keep CU naming compatible with discovery pattern or update discovery code.

How Each Part Works

  • Kernel: For each chunk, SHA-256 digest is computed and 8 words are written to output.
  • Host reference: The same chunk is hashed in software and compared to FPGA digest.
  • Manager: Uses wordsPerChunk = 8 for HASH mode, 1 for CRC/TCP.
  • Result check: Terminal prints digest/checksum lines with [OK] or [MISMATCH].

Important: SHA mode is chunk-based. It is not a single full-file digest unless chunk size equals the file size.

How SHA-256 Works (Professor-Ready)

SHA-256 takes any input length and produces a fixed 256-bit digest (32 bytes). It is a compression-based algorithm that processes data in 512-bit blocks (64 bytes).

  • Step 1 - Padding: Append a 1 bit, then 0 bits, then the 64-bit original length so total size is a multiple of 512 bits.
  • Step 2 - Initialize State: Start from 8 fixed 32-bit initial words (H0..H7).
  • Step 3 - Message Schedule: Build W[0..63] where first 16 words come from the current block, and the rest are expanded with rotate/shift functions.
  • Step 4 - 64 Compression Rounds: Update working variables a..h using SHA-256 boolean/rotate functions (Ch, Maj, BigSigma, SmallSigma) and constant table K[0..63].
  • Step 5 - State Update: Add the final a..h back into H0..H7.
  • Step 6 - Final Digest: Concatenate H0..H7 to get the 256-bit output.

How this project uses SHA-256:

  • Hashing is chunk-based, not streaming across the full file by default.
  • Each chunk is hashed independently, and FPGA writes 8 x uint32_t per chunk.
  • Host software computes the same digest and compares with FPGA output for verification.

Simple talking points for presentation:

  • SHA-256 always outputs 256 bits regardless of input size.
  • Internally it processes 64-byte blocks and runs 64 rounds per block.
  • In our accelerator, each chunk is one SHA job and returns 8 words.
  • We validate FPGA results against a software SHA-256 reference implementation.

FPGA SHA-256 Example (Step-by-Step)

Example: input is abcabc (hex: 61 62 63 61 62 63), mode is HASH, and chunkSize = 3. So FPGA processes 2 chunks: abc and abc.

Step What FPGA/Host Path Does Data Snapshot
1. Chunk split Manager splits input by chunkSize. Chunk0 = 61 62 63, Chunk1 = 61 62 63
2. Kernel launch Manager sets args: numChunks=2, chunkSize=3, mode=HASH. Output buffer reserved for 2 * 8 = 16 words
3. Per-chunk loop process_hash() loops over chunks (c=0,1). Chunk pointer = data_in + c*chunkSize
4. Padding inside SHA sha256_process_chunk(): for each 3-byte chunk, no full 64-byte blocks, so one padded block is built. 61 62 63 80 00 ... 00 00 00 00 00 00 00 18 (24-bit length)
5. Compression sha256_compress() runs 64 rounds using W[0..63] and K[0..63]. State updates from initial H0..H7 to final digest words
6. Write digest Kernel writes 8 digest words to global output. Chunk0 -> crc_out[0..7], Chunk1 -> crc_out[8..15]
7. Host compare Host computes software SHA-256 and compares each 8-word digest. Both chunks match ba7816bf...f20015ad (SHA-256 of abc)

Why both outputs are identical here: both chunks contain the exact same bytes (abc), and SHA-256 is deterministic.

For your default SHA_256 config (chunkSize=1024): each chunk has 16 full 64-byte blocks plus one final padding block, so the kernel performs 17 compression calls per chunk.
